# 订单完整生命周期详解

## 一、订单状态机总览

```
                    ┌──────────┐
                    │ 用户下单  │
                    └────┬─────┘
                         ▼
                  ┌─────────────┐    30分钟超时/用户取消    ┌──────────┐
                  │ PENDING_PAY │ ───────────────────────► │ CANCELED │  (终态)
                  └─────┬───────┘                          └──────────┘
                        │ 支付(mockPay)
                        ▼
                   ┌──────────┐
                   │   PAID   │  押金状态同步变为 PAID
                   └────┬─────┘
                        │ 出租人发货(ship)
                        ▼
                   ┌──────────┐
                   │ TO_SHIP  │  记录快递单号
                   └────┬─────┘
                        │ 承租人确认收货(receive)
                        ▼
                   ┌───────────┐
                   │ TO_RETURN │  租赁中
                   └────┬──────┘
                        │ 承租人申请归还(applyReturn)
                   ┌────┴────┐
                   ▼         ▼
            ┌──────────┐  ┌──────────┐
            │ RETURNED │  │ OVERDUE  │
            │ (按时归还) │  │ (逾期归还) │
            └────┬─────┘  └────┬─────┘
                 │              │
                 └──────┬───────┘
                        │ 出租人确认归还(confirmReturn)
                        ▼
                   ┌──────────┐
                   │ FINISHED │  (终态) 押金状态变为 REFUNDED
                   └──────────┘
```

**8个订单状态**：

| 状态 | 含义 |
|------|------|
| `PENDING_PAY` | 订单已创建，等待支付 |
| `PAID` | 已支付，等待出租人发货 |
| `TO_SHIP` | 出租人已确认发货（设备运输中） |
| `TO_RETURN` | 承租人已收货，租赁进行中 |
| `RETURNED` | 承租人申请归还（按时） |
| `OVERDUE` | 承租人申请归还（逾期） |
| `FINISHED` | 出租人确认归还，订单完成 |
| `CANCELED` | 订单已取消（用户取消或超时） |

**3个押金状态**：

| 状态 | 含义 |
|------|------|
| `UNPAID` | 押金未收取 |
| `PAID` | 支付时收取押金 |
| `REFUNDED` | 确认归还后退还押金 |

押金状态独立流转：`UNPAID → PAID(支付时) → REFUNDED(确认归还时)`

终态：`FINISHED` 和 `CANCELED`，无法再转换。

## 二、每个阶段的业务逻辑

### 1. 创建订单 (`OrderService.createOrder`)

| 步骤 | 逻辑 |
|------|------|
| 校验身份 | 从 `X-User-Id` 请求头获取当前用户，必须登录 |
| 校验时间 | `startTime < endTime`，且 `endTime` 必须在未来 |
| 查询设备 | 通过 Feign 调用 Device Service，设备必须存在且状态为 `ACTIVE` |
| 禁止自租 | `当前用户ID ≠ 设备所有者ID`，不能租自己的设备 |
| 计算租金 | `日租金 × (天数+1)`，首尾日都算 |
| 优惠券校验 | 若传了 `couponId`，通过 Feign 校验：状态=已发布、满足使用门槛 |
| 计算实付 | `payAmount = max(0, totalRent - discountAmount)` |
| 锁定设备 | Feign 调用 `lockDevice()`，原子操作 `ACTIVE → RENTED`，防止并发重复下单 |
| 生成订单号 | `ORD-` + 16位大写UUID |
| 插入订单 | 状态=`PENDING_PAY`，押金状态=`UNPAID` |
| 核销优惠券 | Feign 调用 `consumeCoupon()`，**失败不影响订单创建**（仅记警告日志） |
| 防重复提交 | `@RepeatSubmit(interval=5)` 注解，5秒内不允许重复提交 |

### 2. 支付 (`OrderService.mockPay`)

- **模拟支付**，没有对接真实支付网关
- 权限校验：只有承租人或管理员可操作
- 原子 SQL：`UPDATE order SET status='PAID', deposit_status='PAID' WHERE id=? AND status='PENDING_PAY'`
- 利用乐观锁防并发：如果状态已变更，更新返回0行，抛出 `ORDER_STATUS_ERROR`

### 3. 发货 (`OrderService.ship`)

- 权限校验：只有出租人（设备主人）或管理员可操作
- 原子状态变更：`PAID → TO_SHIP`
- 将快递单号存入 `virtualOrderNo` 字段
- 通过 Outbox 发送 MQ 通知给承租人："您的订单已发货"

### 4. 确认收货 (`OrderService.receive`)

- 权限校验：只有承租人或管理员可操作
- 原子状态变更：`TO_SHIP → TO_RETURN`
- 通过 Outbox 发送 MQ 通知给出租人："承租人已确认收货"

### 5. 申请归还 (`OrderService.applyReturn`)

- 权限校验：只有承租人或管理员可操作
- **关键逻辑**：根据当前时间判断是否逾期
  - `当前时间 ≤ endTime` → 状态变为 `RETURNED`（按时归还）
  - `当前时间 > endTime` → 状态变为 `OVERDUE`（逾期归还）
- 通过 Outbox 发送 MQ 通知给出租人："承租人申请归还"

### 6. 确认归还 (`OrderService.confirmReturn`)

- 权限校验：只有出租人或管理员可操作
- 接受 `RETURNED` 和 `OVERDUE` 两种状态（SQL 用 `IN` 子句）
- 原子状态变更：`RETURNED/OVERDUE → FINISHED`
- 同时将押金状态改为 `REFUNDED`
- `condition`（设备状况描述）参数仅记日志，不存入订单表
- 通过 Outbox 发送 MQ 通知给承租人："归还已确认，押金已退"

### 7. 取消订单 (`OrderService.cancel`)

- 权限校验：只有承租人或管理员可操作
- 只有 `PENDING_PAY` 状态可取消
- 原子状态变更：`PENDING_PAY → CANCELED`
- 发送补偿事件（通过 Outbox）：
  - 设备库存释放（恢复 `ACTIVE` 状态）
  - 优惠券回滚（恢复可用状态）

## 三、定时任务

| 任务 | 频率 | 功能 |
|------|------|------|
| `OrderTimeoutJob` | 每60秒 | 扫描 `PENDING_PAY` 且创建超过30分钟的订单，自动取消并触发补偿 |
| `OutboxPublishJob` | 每5秒 | 将 `mq_outbox` 表中 `NEW/FAILED` 状态的消息发送到 RabbitMQ |
| Outbox 清理 | 每天凌晨4点 | 删除30天前的 `SENT` 消息记录 |

超时窗口30分钟为硬编码值。超时取消与用户取消走相同的补偿流程。

## 四、MQ 消息架构

采用 **Outbox 模式** 保证消息与数据库事务的一致性：

```
订单状态变更 ──同一事务──► mq_outbox 表写入
                              │
                    OutboxPublishJob 轮询(每5秒)
                              │
                              ▼
                      RabbitMQ Topic Exchange
                      camera.rental.order.topic.v1
                     ┌────────┼────────┐
                     ▼        ▼        ▼
              user.notify.q  device.sync.q  coupon.sync.q
              (用户通知)      (设备库存释放)    (优惠券回滚)
```

### 队列与路由

| 队列 | 路由键 | 消费方 | 用途 |
|------|--------|--------|------|
| `user.notify.q` | `order.*.notify.user` | User Service | 用户通知（发货/收货/归还/确认） |
| `device.sync.q` | `order.cancelled.release.stock` | Device Service | 取消时释放设备库存 |
| `coupon.sync.q` | `order.cancelled.rollback.coupon` | Coupon Service | 取消时回滚优惠券 |

每个队列都有对应的死信队列（DLQ），用于处理消费失败的消息。

### 事件类型

- `OrderNotificationEvent`：携带 `userId`、`content`、`messageType`，用于发货/收货/归还/确认通知
- `OrderCancelledEvent`：携带 `orderNo`、`userId`、`deviceId`、`couponId`，用于取消时的补偿操作

### 消息可靠性保证

**发送端**：
- Outbox 模式：消息与业务操作在同一事务中写入 `mq_outbox` 表
- 失败重试：指数退避（5s × 2^N），上限300秒，最多10次
- 状态流转：`NEW → SENT`（成功）或 `NEW → FAILED`（重试耗尽）

**消费端**：
- `mq_consume_log` 表做幂等，`event_id + consumer` 唯一约束
- 重复消费直接跳过（`DuplicateKeyException` → ack）
- 消费失败 nack 不重入队，进入死信队列

## 五、跨服务调用关系

```
Order Service ──Feign──► Device Service   查询设备、锁定库存
Order Service ──Feign──► Coupon Service   校验优惠券、核销优惠券
Order Service ──Feign──► User Service    发送站内消息
Order Service ──MQ outbox──► User Service   发送站内通知

Order Service ──MQ──► Device Service   取消时释放库存
Order Service ──MQ──► Coupon Service   取消时回滚优惠券

Device Service ──Feign──► Order Service   删除设备前检查有无活跃订单
```

## 六、优惠券使用

### 下单时

1. `OrderCreateRequest` 可选传入 `couponId`
2. Feign 调用 `couponFeignClient.getById()` 获取优惠券详情
3. 校验：必须存在、状态=已发布、满足使用门槛
4. `discountAmount = coupon.denomination`（面额全额抵扣，但 `payAmount` 不低于0）
5. 订单入库后 Feign 调用 `consumeCoupon()` 标记已使用
6. **该调用与订单插入不在同一事务中**——失败仅记警告，订单不回滚

### 取消时

- `OrderCancelledEvent` 发送到两个队列：
  - `DEVICE_SYNC_QUEUE`：释放设备库存
  - `COUPON_SYNC_QUEUE`：回滚优惠券
- Coupon Service 的 `OrderCancelledRollbackCouponConsumer` 消费事件并恢复优惠券

## 七、评价系统（订单完成后）

订单状态变为 `FINISHED` 后，承租人和出租人可以互相评价。

**规则**：
- 只有 `FINISHED` 状态的订单可评价
- 只有订单参与者（承租人或出租人）可评价
- 每个参与者每笔订单只能评价一次
- 评分1-5星，内容经 HTML 消毒处理
- 图片路径经 MinIO 规范化
- `evaluatedId` 和 `deviceId` 由服务端计算，不信任前端传值

**回复**：被评价方可回复一次，回复内容也经消毒处理。

**删除**：仅评价者本人可删除自己的评价。

## 八、错误处理与边界情况

### 乐观并发控制

所有状态变更使用原子条件 SQL 更新：`WHERE status = expectedStatus`。如果状态已变更（如双击、并发请求），更新返回0行，抛出 `ORDER_STATUS_ERROR` 异常。

### Feign 熔断

三个 Feign 客户端（Device、Coupon、Message）均有 Fallback 类。下游服务不可用时：
- Device fallback：返回错误结果，订单创建抛出 `SYSTEM_ERROR`
- Coupon fallback：返回错误结果，订单创建抛出 `SYSTEM_ERROR`
- Message fallback：返回错误结果（非关键路径）

Sentinel 已启用（`feign.sentinel.enabled: true`）。

### 逾期检测

逾期判断发生在承租人**申请归还的那一刻**，而非定时任务扫描。如果 `LocalDateTime.now().isAfter(order.getEndTime())`，状态设为 `OVERDUE` 而非 `RETURNED`。

### 活跃订单检查

`hasActiveOrders(deviceId)` 检查设备是否有非终态订单（除 `FINISHED` 和 `CANCELED` 外的所有状态）。Device Service 通过 Feign 调用此接口，防止删除有活跃订单的设备。

## 九、数据库表结构

### order 表

```sql
CREATE TABLE `order` (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  order_no VARCHAR(64) NOT NULL UNIQUE,
  user_id BIGINT NOT NULL,          -- 承租人
  device_id BIGINT NOT NULL,
  lessor_id BIGINT NOT NULL,        -- 出租人
  start_time DATETIME NOT NULL,
  end_time DATETIME NOT NULL,
  total_rent DECIMAL(10,2) NOT NULL,
  deposit DECIMAL(10,2) NOT NULL,
  coupon_id BIGINT DEFAULT NULL,
  discount_amount DECIMAL(10,2) NOT NULL DEFAULT 0.00,
  pay_amount DECIMAL(10,2) NOT NULL,
  virtual_order_no VARCHAR(64) DEFAULT NULL,  -- 快递单号
  status ENUM('PENDING_PAY','PAID','TO_SHIP','TO_RETURN','RETURNED','OVERDUE','FINISHED','CANCELED') NOT NULL,
  deposit_status ENUM('UNPAID','PAID','REFUNDED') NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_order_status_created (status, created_at)  -- 超时任务使用
);
```

### 相关支撑表

- `mq_outbox`：Outbox 模式消息暂存
- `mq_consume_log`：消费端幂等记录
- `evaluation`：订单评价
- `operation_log`：操作日志

## 十、关键设计亮点

1. **乐观并发控制**：所有状态变更用 `WHERE status = expectedStatus` 条件更新，防双击/并发
2. **Outbox 模式**：MQ 消息与业务操作在同一事务中写入，避免数据不一致
3. **幂等消费**：消费端通过唯一约束保证消息不会被重复处理
4. **补偿机制**：取消订单时自动释放库存 + 回滚优惠券，通过 MQ 异步执行
5. **Feign + Sentinel 熔断**：下游服务不可用时走 fallback，不会拖垮主流程
6. **防重复提交**：`@RepeatSubmit` 注解防止前端双击导致重复下单
